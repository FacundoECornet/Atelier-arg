**Step A — firestore.rules (new file in project root):**

Create `firestore.rules` with these exact rules:
```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /{document=**} {
      allow read: if true;
      allow write: if request.auth != null;
    }
  }
}
```
The wildcard `{document=**}` matches every document at any depth — covers all 3 collections (propiedades, Noticias, Nosotros). Reads are public. Writes require Firebase Auth authentication.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client (any browser) → Firestore | Reads are public (`allow read: if true`). Writes cross trust boundary — require authentication. |
| Firebase Auth → Firestore Rules | `request.auth != null` — server-side check, client cannot forge auth state. |
| Netlify build → Client bundle | Env vars injected at build time (`import.meta.env.VITE_*`) — values visible in JS bundle (by design, not secrets). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-07 | Tampering | Firestore writes (browser console) | mitigate | Firestore rules: `allow write: if request.auth != null` — server-side enforcement, client JS bypass impossible. |
| T-02-08 | Elevation of Privilege | Firestore rules (misconfiguration) | mitigate | Rules use wildcard `{document=**}` — applies uniformly to all 3 collections. No per-collection gap. |
| T-02-09 | Information Disclosure | .env.example | accept | Template uses placeholder values (`your_api_key`, `your_project_id`). No real secrets. Safe to commit. |
| T-02-10 | Denial of Service | Firestore reads (unauthenticated) | accept | `allow read: if true` — unlimited public reads. Firebase has built-in quotas. Sufficient for real estate site traffic. |
| T-02-11 | Information Disclosure | Netlify env vars in build | accept | VITE_ prefixed vars embedded in client JS — Firebase config values are project identifiers, not secrets. Real security is in Firestore rules + Firebase Auth (server-side). |
| T-02-12 | Elevation of Privilege | Atomic deploy timing | mitigate | Documented deploy order: code → Netlify first, then rules. Never deploy rules solo. Out-of-order deploy breaks admin panel. |
</threat_model>
